01무엇을 자동화했나

이 경계선이 이 프로젝트의 전부다. 어디까지 사람이고 어디부터 코드인지가 흐려지면 자동화라는 말은 의미가 없다.

제작 단위는 세트다. 롱폼 1편(5~8분) + 그 내용에서 뽑은 쇼츠 3편. 한 세트를 만드는 동안 사람이 키보드를 잡는 순간은 세 번이고, 그 사이는 전부 저장소 안의 CLI가 채운다.

사람이 하는 일 — 3곳

  • ① 기획 — 주제·훅·목표 길이를 정한다. 완료 기준은 "첫 5초 훅과 엔딩이 한 문장으로 정리됐나".
  • ② 최종 시사 — QA 콘택트 시트와 의심 구간 원본 프레임을 눈으로 본다. 숫자 검증만으로는 통과시키지 않는다.
  • ③ 발행 승인 — 완성본은 언제나 비공개로 먼저 올라간다. 명시적 승인 시각이 기록되기 전에는 공개도 예약도 하지 않는다.

저장소가 하는 일

  • 씬 타임라인 컴파일 — 씬 ID + 상대 오프셋 → 절대 프레임. 프레임이 유일한 타이밍 권위다.
  • 나레이션·자막 — TTS 생성(캐시·영수증 포함), 실측 클립 길이 기반 번인 자막 JSON 생성.
  • 섹션 영상 — 정보 씬(코드 렌더), 손그림 씬, 시네마틱 컷 배치.
  • 오디오 — BGM cue 배치, 나레이션 구간 자동 덕킹, kind 전환마다 whoosh 자동 삽입.
  • 검증 — 구조·출처·에셋·타이밍 preflight, 페이싱 규칙 검사, 라우드니스 정규화, 전달 규격 QA.
  • 재현성 — 렌더 입력 전부 Git 추적·HEAD 일치 강제. 커밋되지 않은 입력으로는 최종본을 만들 수 없다.
공개·예약은 승인 전에 절대 하지 않는다. QA를 통과했고 업로드 ID가 있어도, 승인 시각이 기록되지 않은 상태에서는 상태 전이를 멈춘다. 이건 기술 제약이 아니라 운영 규칙이고, 발행 대장의 상태 모델(draft → rendered → qa_passed → uploaded_private → approved → scheduled/published)이 그걸 강제한다.

렌더 명령의 기본값은 "아무것도 하지 않기"다. npm run render는 결정론적 계획만 출력하고 파일도 프로세스도 건드리지 않는다. --execute를 명시해야 편별 production lock을 잡고 strict preflight부터 순서대로 실행한다. --skip-qa로 만든 UNVERIFIED-*.mp4는 canonical final을 갱신하지 않으며 발행 후보가 아니다.

실행 순서--execute 가 한 프로세스에서 하는 일

production lock 획득
→ strict production preflight (Git 추적 · HEAD 일치 · 전체 미디어 디코드)
→ 콘텐츠 fingerprint / 출력 SHA-256 청크 캐시 검증
→ 씬 경계 video-only 청크 렌더 (최대 1,600프레임)
→ strict concat 프레임 · timestamp cadence 검증
→ 48kHz PCM WAV 오디오를 같은 청크 경계로 렌더 후 무손실 concat
→ 임시 MOV mux → finalize (loudnorm + 리미터) → staged 전달 규격 검증 → QA
→ 통과한 staged 파일만 atomic rename으로 out/<id>/final.mp4 승격

실패하면 기존 final은 그대로 남는다. 승격은 같은 파일시스템 안의 atomic rename이라 반쯤 쓰인 최종본이 존재할 수 없다.

재사용이 원가에 어떻게 작용했나

1~6호

유료 생성기를 편마다 호출했다. 크레딧을 쓴 편의 평균 원가는 ₩5,886.

7~10호

라이브러리에서 꺼내 썼다. 크레딧 사용 0. 남은 비용은 사실상 나레이션 글자 수뿐이다.

첫 사용 비율

9호는 영상 컷 24개가 전부 첫 사용, 10호는 paper 12컷 중 7컷이 첫 사용이었다. 재고가 실제로 소비되고 있다.

재고 운영 규칙

  • BGM은 영상 제작 중에 만들지 않는다. 별도 세션에서 미리 만들고 검수해 라이브러리에 넣는다. 렌더 중에 생성 도구를 호출하면 8GB 메모리와 집중이 동시에 깨진다.
  • 라이브러리 등록 ≠ 사용 가능. 스테이징 디렉터리는 Git 밖이고, 편이 실제로 쓰는 파일만 추적 디렉터리로 복사해 커밋한다. production preflight는 tracked만 통과시킨다.
  • BGM 파일은 SHA-256으로 고정한다. 같은 이름의 로컬 파일이 발행된 편집본을 바꾸지 못하게 막는다. 파생 클립은 원본 트랙 ID와 정확한 발췌 시작점을 기록한다.
  • 새 스톡은 HTTPS 원본 URL·라이선스·SHA-256이 없으면 채택하지 않는다. 과거 다운로더가 URL을 보존하지 않은 4개만 소급 예외로 경고를 허용하고, 새 편에서는 같은 예외를 만들지 않는다.

04품질 게이트

"돌려봤더니 됐다"는 통과 기준이 아니다. 게이트는 세 층이고, 마지막 층은 사람 눈이다.

layer 1preflight — 개발 게이트 vs production 게이트

같은 계약을 검사하지만 Git 상태를 다루는 방식이 다르다. 개발 중에는 미추적·dirty 입력을 집계 경고로 보여주고 작업을 막지 않는다. production에서는 그게 하드 실패다.

layer 2validatePacing — 지루한 구성을 코드가 거부한다

스타일 가이드의 페이싱 문법을 그대로 검사로 옮긴 것이다. Studio 콘솔과 렌더 로그에 경고로 뜬다.

  • B-roll단일 스톡 컷 8초 초과 금지 — 나레이션 한 문장을 받쳐주고 빠진다
  • B-roll스톡 컷 연속 배치 금지 — 사이에 반드시 다른 모드가 들어간다
  • B-roll전체 분량의 15% 이하 — "대본+TTS+스톡 영상"은 양산형 판정의 대표 패턴이다
  • 페이싱같은 kind가 연속 50초를 넘으면 경고 — 시각 모드는 40~50초마다 바뀐다
  • 페이싱히어로 컷 없이 120초가 지나면 경고 — 히어로는 챕터 전환의 문장 부호다
  • 브랜드인트로는 콜드오픈 바로 뒤, 아웃트로는 마지막 씬이어야 한다

layer 3QA — 전달 규격 하드 게이트

하나라도 어긋나면 최종본이 승격되지 않는다. 경고와 하드 실패를 명확히 나눈다.

  • FAILH.264 영상 1개 + AAC 오디오 1개 + 그 밖의 stream 0개 — 데이터 트랙이나 챕터 스트림이 섞이면 실패
  • FAIL해상도 1920×1080 또는 1080×1920
  • FAIL프레임별 30fps timestamp cadence — 허용 오차 1ms. VFR과 concat 이음매를 잡는 게이트다
  • FAILyuv420p · TV-range · BT.709 (색공간·primaries·transfer 전부)
  • FAIL48kHz stereo · A/V 길이 차이 50ms 이하 · 전체 디코드 성공

오디오2-pass loudnorm + 리미터

1차 패스로 loudnorm 측정값(I / LRA / TP / thresh / offset)을 뽑고, 2차 패스에서 linear=true로 한 번에 게인을 건다. 그 뒤에 alimiter=limit=-1.5dB를 붙인다.

리미터를 붙인 건 10호에서 TP=-1.5를 걸고도 실측 -0.9 dBFS가 나와 하드 게이트(-1.0)에 걸렸기 때문이다. 9호는 -1.3으로 운 좋게 통과했었다. loudnorm의 TP는 목표이지 보장이 아니다.

layer 4사람 눈 — 콘택트 시트로 끝내지 않는다

축소 이미지에서는 겹침이 보이지 않는다. 6호 검수에서 결함 5건을 잡았는데 그중 하나는 콘택트 시트에서 전혀 보이지 않았다. 그 뒤로 의심 구간은 ffmpeg -ss <초> -frames:v 1로 실물 크기 프레임을 뽑아 확인한다. 숫자 검증만으로 통과시키지 않는다는 원칙이 여기서 나왔다.

섹션 컴포지션은 하단 150px(y ≥ 930)을 비워 설계한다. 번인 자막이 거기 깔리기 때문이다. 섹션 하단에 나레이션과 같은 문장을 넣는 것도 금지다 — 자막과 중복돼 같은 문장이 두 번 보인다. 아웃트로는 유튜브 엔드스크린 카드가 마지막 5~20초에 겹치므로 가운데 띠(세로 24~74%)를 비우고, 검수할 때 drawbox로 카드 자리를 그려 침범 여부를 눈으로 본다.

068GB 안에서 5~6분짜리를 렌더하기

메모리가 부족하면 렌더는 실패하지 않는다. 조용히 멈춘다. 그게 더 나쁘다.

이 파이프라인은 메모리 8GB 머신에서 돈다. 5~6분 롱폼은 30fps 기준 9,000~11,000프레임이고, 한 번에 렌더하면 중간에 죽는다. 죽는 방식이 명확한 에러가 아니라 "10~12분 돌다가 프로세스가 사라짐"이라 원인을 찾는 데 시간이 걸렸다.

씬 경계 청크 분할

최대 1,600프레임, 반드시 씬 경계에서 자른다. 한 씬 자체가 상한을 넘으면 씬을 먼저 나눈다. 고정 시간으로 자르지 않는 이유는 청크 경계가 씬 경계와 어긋나면 재렌더 단위가 무의미해지기 때문이다.

포그라운드 순차 처리

3,000프레임을 백그라운드로 돌리면 10~12분 뒤 중간 종료된다(3회 연속 재현). --concurrency=2로 낮춰도 같았다. 포그라운드 소청크가 3배 빠르고 안정적이다.

콘텐츠 fingerprint 캐시

청크 입력 fingerprint와 출력 SHA-256을 함께 검증한다. --resume은 검증된 청크만 재사용하고 손상·불일치 캐시는 다시 만든다. --changed <scene-id,...>는 해당 씬이 든 청크만 강제 재렌더한다.

편별 production lock

E2E 렌더끼리뿐 아니라 나레이션 compile과 렌더의 동시 실행도 차단한다. 죽은 PID의 stale lock도 자동 삭제하지 않는다 — 실제 프로세스를 먼저 확인한다.

오디오도 청크로 렌더해야 한다. 영상은 진작 1,600프레임으로 쪼갰는데 오디오만 통짜 패스였다. 프레임 9,500쯤부터 Chrome이 버티지 못하고 폰트 delayRender가 영영 풀리지 않는다. 10,734프레임짜리 10호에서 3회 재현했고, 9,534프레임이었던 9호는 아슬하게 통과했었다. 지금은 오디오도 같은 씬 경계 청크로 렌더한다 — PCM WAV라 이어붙여도 무손실이고 샘플 경계가 어긋나지 않는다.

렌더 중에는 다른 무거운 작업을 일절 돌리지 않는다. ffmpeg 먹싱·정규화도 포함이다. 여유 메모리가 500MB까지 떨어지는 구간이 있다.

이 섹션이 이 문서에서 제일 쓸모 있는 부분이다. 원인을 찾는 데 걸린 시간이 곧 이 파이프라인의 원가였다.

컨테이너와 타임스탬프

01MKV 중간 컨테이너가 30fps 케이던스를 깬다

영상 청크를 이어붙인 뒤 오디오와 합칠 중간 컨테이너로 MKV를 썼다. MKV는 PTS를 1ms 단위로 반올림한다. 30fps의 프레임 간격은 33.333…ms라서 프레임마다 오차가 쌓인다. QA의 프레임별 timestamp cadence 하드 게이트가 이걸 잡아냈다.

지금은 중간 컨테이너를 MOV + pcm_s16le로 쓴다. 영상은 stream-copy, 오디오는 무압축 PCM이라 반올림이 개입할 곳이 없다.

scripts/render-master.ts · 커밋 "E2E 렌더 중간 컨테이너를 MKV → MOV"

02AAC MP4 중간본은 정확히 +100ms A/V 드리프트를 만든다

쇼츠 조립에서 중간본을 AAC MP4로 두면 최종본의 오디오가 영상보다 정확히 100ms 밀린다. "정확히 100ms"라서 오히려 원인 추적이 됐다 — 랜덤 오차가 아니라 인코더 프라이밍 지연이다.

지금은 쇼츠도 롱폼과 같은 MOV + PCM 중간본을 쓴다. -af와 complex filtergraph를 함께 못 쓰기 때문에 믹스·패딩·트림·loudnorm을 전부 filtergraph 안에서 끝낸다.

scripts/shorts-assemble.sh 상단 주석 (8호 실측)

03오디오가 든 MP4 청크를 concat-copy하면 경계마다 48ms가 튄다

AAC 프레임 패딩 때문에 청크 이음매마다 48ms의 timestamp 점프가 생겼고, 7호에서 총 240ms가 실측됐다.

지금은 영상 청크만 concat하고, 오디오는 별도로 렌더해서 한 번에 붙인다. 영상과 오디오의 조립 경로를 분리한 게 핵심이다.

WORKFLOW.md §6

04loudnorm의 True Peak는 목표지 보장이 아니다

TP=-1.5를 걸고 linear=true로 정규화했는데 10호 최종본이 -0.9 dBFS로 나왔다. QA 하드 게이트는 -1.0이라 거기서 막혔다. linear 모드는 게인을 한 번에 걸기 때문에 소재에 따라 천장을 넘는다. 9호는 -1.3으로 운 좋게 통과했던 것이고, 그때 발견했으면 더 좋았을 문제다.

지금은 loudnorm 뒤에 alimiter=limit=-1.5dB를 붙여 천장을 실제로 강제한다. 마감 스크립트가 최종 LUFS·TP를 다시 읽어 기준을 벗어나면 실패시킨다.

생성 모델의 한계

05생성 모델은 한글·한자를 쓰지 못한다 — 그래서 정보 화면은 전부 코드가 그린다

실제로 나온 결함들이다. 달력 컷에 25가 두 번 찍혔다. 담벼락 격문에는 또렷한 가짜 한자가 나왔는데 읽을 수 있는 글자가 하나도 없었다. 연표를 그려달라고 했더니 눈금만 늘어났다. 생성 모델은 글자를 글자로 쓰는 게 아니라 글자처럼 보이는 그림을 그린다 — 영어는 얼추 맞고 획이 많은 한글·한자는 무너진다.

8호에서 A/B로 확인했다. 같은 연표 구간을 코드 렌더로 만들면 연도와 인명을 순차로 찍고 공백 구간을 브레이스로 시각화하는데, 생성 컷은 눈금만 늘어난다. 프롬프트로 해결되는 문제가 아니다.

지금은 역할을 나눈다 — 연표·데이터·고유명사는 코드 렌더, 정서·비유·회상은 생성 컷. 매 영상에 박히는 채널 워드마크도 배경만 생성 컷이고 한글은 코드로 얹는다.

assets/grok/library.json findings · 10호 편 전체가 이 주제다

06"illegible" 한 단어로는 글자가 뭉개지지 않는다

글자가 나오는 장면에 "읽을 수 없게"라고만 쓰면 또렷한 가짜 글자가 나온다. 야간 + 급한 측면 각도 + 찢김·얼룩 + "faded into illegible grey smudges with no distinct characters"를 함께 걸어야 실제로 뭉개진다.

세이프티 필터도 같은 방식으로 우회한다 — 동작 표현("붓이 종이에 닿는다")이 차단되면 정물("붓이 벼루에 놓여 있다")로 바꾼다.

07개수 결함은 부정문만으로 잡히지 않는다

달이 두 개 나오는 컷이 반복됐다. "달은 하나"라고 쓰는 것으로는 부족했고, "exactly one single moon" + "only one moon in the entire frame" + "no second moon, no reflection, no lens flare"를 함께 걸어야 해결됐다. 개수는 프레임마다 달라질 수 있어서 5지점을 확인한다.

인물도 같다. "Faces not visible"만으로는 3/4 측면 얼굴이 또렷하게 나왔다. 뒷모습을 명시적으로 고정하는 문구를 함께 걸어야 막히고, 중간에 돌아설 수 있어서 시작·중간·끝 3프레임을 본다.

08생성기가 만든 종이는 손그림 종이보다 항상 노랗고 어둡다

같은 "미색 종이"를 요청해도 생성 컷은 #EBE3CC, 손그림 렌더는 #F3EFE0로 나온다. 섞어 붙이면 종이가 두 종류로 보인다.

지금은 회수 직후 colorbalance + eq로 보정한 뒤에야 라이브러리에 넣는다. 밝은 종이 컷과 어두운 감성 일러스트도 서로 다른 구간에만 쓴다.

브라우저 자동화

09예약 시각은 JS로 input.value를 세팅할 수 없다

네이티브 setter를 쓰고 input·change 이벤트까지 보내도 화면의 값만 바뀌고 컴포넌트 내부 상태는 바뀌지 않는다. 확인 문구가 "0:00"으로 나와 자정 예약이 걸렸고, 편집 페이지에서 실제 클릭·타이핑으로 다시 고쳐야 했다.

지금은 날짜는 달력 셀 클릭, 시각은 실제 타이핑만 신뢰한다. 절차도 고정했다 — 필드 클릭 → document.activeElement의 tag와 value 확인 → 전체 선택 → 타이핑 → 코드포인트 검증 → Enter → 목록에서 예약 시각 재확인.

10날짜만 바꾸면 시각이 과거로 남아 즉시 게시된다

공개 상태 단계에서 날짜만 변경하면 시각은 기본값(이미 지난 시각)으로 남는다. 예약 버튼이 비활성화되고 빨간 경고가 뜨는데, 그대로 진행하면 예약이 걸리지 않은 채 즉시 게시된다. 이걸로 쇼츠 6편이 새벽에 나가 0~9회로 죽었다. 시간대 설정은 정상이었다 — 시간대는 원인이 아니었다.

지금은 저장 후 Studio 목록에서 "예약됨 + 정확한 시각"까지 눈으로 확인하는 항목이 세트 종료 체크리스트에 들어가 있다.

11한글 입력은 조합이 깨진다

브라우저 자동화의 일반 타이핑 액션이 한글 조합을 잘못 처리해 "썰"이 "썬"으로 들어갔다. 제목·설명처럼 틀리면 안 되는 필드에서 이게 발생하면 발행 자체가 사고가 된다.

지금은 execCommand('insertText')로 넣고 코드포인트 단위로 검증한다.

12좌표 클릭은 창 크기가 바뀌는 순간 사고가 된다

에셋 회수 화면에서 다운로드 버튼과 삭제 버튼이 40px 간격이다. 창 폭이 1568에서 1440으로 바뀌자 같은 좌표가 삭제 버튼에 떨어져 삭제 확인 다이얼로그가 떴다(취소해서 컷은 무사했다).

지금은 좌표 대신 aria-label로 찾아 클릭한다. 부수 효과로 폴링 신호도 생겼다 — 해당 요소가 null이면 아직 생성 중이라는 뜻이라, 컷당 25~35초로 들쭉날쭉한 생성 시간을 고정 대기 없이 기다릴 수 있다.

13브라우저의 연속 자동 다운로드 차단은 우회할 수 없다

배치로 에셋을 회수할 때 크롬이 첫 1회 뒤로 자동 다운로드를 막는다. 좌표 클릭·blob 다운로드·로컬 수신 서버로의 POST를 전부 시도했고 전부 막혔다(사이트 CSP가 localhost도 차단한다).

해결은 하나뿐이다 — 브라우저 설정에서 해당 도메인의 자동 다운로드를 미리 허용해두는 것. 배치 시작 전에 해둘 일로 문서에 박았다. 그리고 다운로드가 막혀도 생성물은 계정에 남으므로 URL만 기록해두면 나중에 회수할 수 있다. 재생성은 불필요하다.

검수와 운영

14영수증 자리값을 그대로 렌더하면 화면에 ₩0이 인쇄된다

원가를 화면에 띄우는 씬이 있는데, 스펙의 영수증 필드가 자리값인 채로 렌더가 돌아 실제로 ₩0이 인쇄된 적이 있다. "원가를 공개한다"가 이 채널의 무기인데 그게 0으로 찍히면 무기가 아니라 흠이다.

지금은 preflight가 영수증 필드에 TODO·추정치가 남아 있으면 실패시킨다. 크레딧 사용량은 생성 전후 잔액 차분으로 구한다.

15자동 세로 변환은 롱폼을 쇼츠로 못 만든다

가로 영상을 세로로 자동 변환하는 기능을 A/B로 검증했고 탈락시켰다. 22초 소스에 22초를 명시했는데 7초로 잘렸고, 2개 변형 중 1개는 실패했다. 결과물은 가로 화면을 세로 캔버스 가운데 레터박스로 박은 형태였고 글자가 읽히지 않는 크기로 축소됐다.

근본 원인은 우리 롱폼이 16:9 레이아웃으로 설계된 타이포 중심 화면이라는 것이다 — 잘라내면 정보가 사라진다. 쇼츠는 세로 전용 컴포지션으로 새로 설계하는 것이 유일한 방법이다. 세로 소재를 롱폼에 쓸 때도 회전·레터박스 대신 라운드 프레임 PiP로 얹는다.

16훅 사전 검증 도구는 우리 포맷에 안 맞았다

영상의 훅 강도를 예측해주는 도구를 도입하려다 제약 두 개에 걸렸다. 완성된 영상만 받고(텍스트 훅 후보를 미리 검증할 수 없다), 16초 이하만 받는다. 우리 쇼츠는 23~25초라 아예 입력이 안 된다.

대체안 — 검색 수요 데이터로 소재와 배치 순서를 정한다. 실제로 특정 주제의 검색량이 다른 주제의 1.5~2배로 나와 그 편을 프라임 시간대에 배치했다.

17내가 설정한 값과 다르면, 결함을 의심하기 전에 물어본다

업로드 중에 롱폼 공개 범위가 비공개에서 공개로 바뀐 걸 발견하고 결함으로 판단해 되돌렸다. 사용자가 시사하려고 직접 바꾼 것이었다. 되돌린 건 불필요한 조치였다.

Studio는 사람도 같이 쓰는 화면이다. 자동화가 단독 소유자가 아닌 환경에서는 "상태가 예상과 다름 = 결함"이 성립하지 않는다. 되돌리기는 확인 뒤에 한다.

18인트로를 맨 앞에 두지 않는다

채널 인트로(5.8초)는 콜드오픈 다음, 씬 인덱스 1에 들어간다. 훅보다 로고가 먼저 나오면 첫 5초 이탈이 커진다. 훅으로 붙잡은 다음에 채널을 보여준다.

preflight가 인트로 위치와 아웃트로 위치, 그리고 두 씬의 소스 오디오 정책(exclusive)을 강제한다. 규칙을 문서에만 적어두면 다음 편에서 잊는다.

08아직 안 된 것

공개하는 김에 구멍도 같이 적는다. 여기 적히지 않은 성과는 아직 없는 성과다.

  • CTR·시청 지속률을 한 번도 수집하지 않았다. 조회수는 목록에서 보이지만 클릭률과 첫 30초 이탈률은 분석 탭에서만 볼 수 있고, 아직 열지 않았다. 그동안의 개선(자막 도입, 효과음 추가, 페이싱 조정)은 전부 감으로 한 것이다. 발행 +48시간 회수 단계를 체크리스트에 넣었지만 실행 기록은 아직 0건이다.
  • 자막 타이밍은 실측 정렬이 아니다. 현재는 실측 TTS 클립 길이 안에서 대본 글자 수에 비례해 배분한다. 로컬 음성인식은 보조 자료로만 쓴다. 보조 TTS 엔진에 단어 단위 타임스탬프 API가 있어서, 엔진을 전환하면 추정을 실측 정렬로 바꿀 수 있다 — 아직 하지 않았다.
  • 쇼츠는 매번 손으로 새로 설계한다. 롱폼에서 훅 3개를 고르고 세로 컴포지션을 새로 만드는 작업이 자동화되어 있지 않다. 자동 클리핑은 위 15번 이유로 탈락했다.
  • 제목 가설과 보이스 선택 가설이 검증 대기 중이다. 상위 조회수 쇼츠는 제목이 주장을 말했고 0회짜리 하나만 주장을 숨겼다는 관찰이 있는데, 표본이 작아 아직 규칙이 아니다.
  • 표본이 작다. 롱폼 10편, 쇼츠 24편이다. 이 문서의 원가·렌더 시간은 실측이지만, 조회수 관련 해석은 전부 이 표본 크기 안에서만 유효하다.
이 문서의 모든 숫자는 저장소 안의 파일에서 나왔다. 편당 원가는 각 편의 스펙에 기록된 실측 사용량을 코드의 요율로 계산한 값이고, 조회수와 발행 상태는 관리 화면에서 직접 확인해 기록한 값이다. 확인하지 못한 값은 추정으로 채우지 않고 비워 둔다 — 대장의 규칙이기도 하다.
